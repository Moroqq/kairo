## Перенос данных с ноутбука на телефон

Актуальная задача: основные задачи и траты лежат в десктопном приложении
на ноутбуке, на телефоне — ничего ценного. Направление переноса
**ноутбук → облако → телефон**, и оно не требует ни смены DNS, ни
совпадения подписи APK.

Порядок:

1. **Ноутбук**: собрать 0.4.8 и поставить поверх (NSIS обновляет на месте,
   данные WebView2 сохраняются). Новая сборка ходит на `kairoupdate…`,
   который уже работает.
2. При первом запуске она сама выгрузит локальные данные в облако —
   см. ниже про защиту. Убедиться на экране SYNC: «облако подключено»
   и свежее время последнего синка.
3. **Телефон**: поставить тот же 0.4.8 (данные телефона не жалко, так что
   можно и с удалением старого APK, если подпись не совпадёт).
4. На телефоне — «подключить к существующему аккаунту», показать QR,
   на ноутбуке — «подключить новое устройство» и отсканировать.
   Телефон получит данные ноутбука.

### Почему первый запуск не затирает данные

Ключи `kairo_sync_last_ts` и `kairo_sync_dirty` появились только вместе
с новым синком, поэтому у обновившегося устройства их нет. Без отдельной
обработки `syncNow()` решил бы, что отдавать нечего, и начал бы с `pull()` —
то есть затёр бы задачи ноутбука снимком из облака.

Поэтому в `vps-sync.service.ts` есть `adoptLegacyLocalData()`: «данные есть,
а истории синка нет» трактуется как несинхронизированные изменения, и
стартовый обмен сначала отдаёт их.

Проверено двумя прогонами в браузере:

| Условие | Что с задачами ноутбука |
|---|---|
| с защитой | сохранились и уехали в облако, телефон их получил |
| без защиты (контрольный опыт) | затёрты содержимым облака |

## Ловушка: .env.local на машине сборки

`.env.local` лежит в `.gitignore`, но Vite отдаёт ему **приоритет над**
`.env.production`. Если в нём остался старый `VITE_KAIRO_SERVER_URL`,
сборка уедет на прежний хост, что бы ни было закоммичено в репозитории —
и выглядеть это будет как «клиент почему-то не видит сервер».

Перед сборкой релиза:

```powershell
Get-Content .env.local -ErrorAction SilentlyContinue
```

Либо удалить файл (тогда возьмётся закоммиченный `.env.production`), либо
поправить в нём адрес на актуальный. Проверить, что попало в сборку:

```powershell
Select-String -Path dist\assets\*.js -Pattern "duckdns\.org" | Select-Object -First 1
```

## Подпись APK и сохранность данных

Данные приложения (задачи, траты, планы) лежат в localStorage WebView.
На Android они переживают обновление **только если новая сборка подписана
тем же ключом**: при несовпадении подписи система требует удалить старое
приложение, а вместе с ним стирается и localStorage.

Проверено 2026-08-24 по файлам репозитория:

| Что | Владелец | SHA-256 |
|---|---|---|
| `kairo.apk` | `CN=Android Debug, O=Android, C=US` | `B9:B5:7B:CA:3A:F0:57:FF:ED:F5:19:AA:BD:91:05:47:9D:5E:DC:D2:68:AA:6D:73:47:13:18:42:4C:67:3A:91` |
| `debug.keystore` (в репо) | `CN=Kairo, O=Kairo, C=RU` | `68:8F:AB:66:B1:90:7E:88:94:C2:37:D9:26:36:34:72:59:4F:97:BB:05:6E:86:4F:AB:14:CC:8C:50:E1:94:CC` |

Ключи **разные**. Прежняя запись в этом файле («вероятно, подписывался
вручную через apksigner») неверна: APK подписан стандартным отладочным
ключом Android SDK из `%USERPROFILE%\.android\debug.keystore`, который
Gradle создаёт сам, когда в `build.gradle.kts` нет `signingConfig`.
Лежащий в репозитории `debug.keystore` к установленным сборкам отношения
не имеет.

Практические следствия:

- Собирать релиз нужно **на той же машине**, где цел
  `%USERPROFILE%\.android\debug.keystore` — тогда подпись совпадёт
  и обновление встанет поверх без потери данных.
- Этот файл надо **забэкапить прямо сейчас**. Если он пропадёт, ни одно
  будущее обновление уже не встанет поверх текущей установки: только
  удаление приложения со стиранием данных.
- Сверить отпечаток перед сборкой:
  ```powershell
  keytool -list -v -keystore "$env:USERPROFILE\.android\debug.keystore" -storepass android -alias androiddebugkey
  ```
- На десктопе проблемы нет: NSIS/MSI обновляют на месте, данные WebView2
  сохраняются.

Второй, независимый способ подстраховаться — сначала выгрузить данные
устройства в облако (тогда переустановка вообще не страшна). Он безопасен,
если в облаке ещё пусто: старая сборка при запуске делает безусловный
`pull()`, и пустой снимок ничего не затирает. Проверить:

```bash
sqlite3 /opt/kairo-server/server/data/kairo.db "SELECT account_id, updated_at, length(data) AS bytes FROM sync_blobs;"
```

Пустой вывод — облако чистое, выгружать безопасно. Есть строка — сначала
разобраться, чей это снимок, иначе старая сборка затрёт им локальные данные.

## Где что делается

Три разных места, их легко перепутать:

| Где | Что там делается | Чего там делать НЕ надо |
|---|---|---|
| **VPS** (`ssh root@45.151.62.223`) | бэкенд: `git pull`, `npm run build`, `systemctl restart`; nginx; публикация файлов релиза в `server/data/update/` | не собирать приложение — там нет ни Rust, ни Android SDK |
| **Локальная машина** (Windows) | сборка десктопа и APK через Tauri, подпись, `git push` | не трогать бэкенд — он живёт только на VPS |
| **Панель DuckDNS** (браузер) | A-записи доменов | — |

Как понять, где ты сейчас — по приглашению строки:

| Приглашение | Где | Что там работает |
|---|---|---|
| `PS C:\...>` | Windows, локально | `npm run tauri`, `git push` |
| `root@147786:~#` | VPS | `systemctl`, `sudo`, `/opt/kairo-server` |

Серверные команды выполняются **после** `ssh root@45.151.62.223` — в
PowerShell они просто не существуют (`sudo`, `systemctl` не найдены,
`/opt/...` читается как `C:\opt\...`).

Ключевое следствие: **чтобы починить синк, локальная машина не нужна вообще.**
Синк — это бэкенд плюс nginx плюс правильный DNS. Локальная сборка нужна
только чтобы доставить на устройства новый код клиента.

## Обновления приложения (`/update/latest.json`)

Раньше этот эндпоинт нигде в репозитории не существовал: и
`src-tauri/tauri.conf.json` (`plugins.updater.endpoints`), и ручной
Android-путь в клиенте ходили за `https://<host>/update/latest.json`,
а сам файл предполагался положенным на VPS руками и раздаваемым отдельным
location в nginx. Нигде не задокументированный, он же и был точкой отказа:
клиент показывал `Failed to fetch`, хотя бэкенд был жив.

Теперь маршрут принадлежит бэкенду — `server/src/routes/updates.ts`:

- `GET /update/latest.json` — отдаёт файл из каталога релизов (читает с диска
  на каждый запрос, рестарт не нужен). Если файла нет — 404 с внятным
  текстом, а не молчание.
- `GET /update/<файл>` — отдаёт сборку (APK/установщик) с правильным
  `Content-Type`; для `.apk` это `application/vnd.android.package-archive`,
  без него Android не предложит установку. Имена файлов проверяются
  регуляркой, выход за каталог невозможен.

Каталог релизов: `$KAIRO_UPDATE_DIR`, по умолчанию `server/data/update/`
(в `.gitignore`). Шаблон манифеста — `server/update.example.json`.

### Как выпустить версию

1. Поднять `version` в `package.json` и `src-tauri/tauri.conf.json` (должны совпадать).
2. Собрать: `npm run tauri -- build` и/или `npm run tauri -- android build --apk`.
3. Скопировать артефакты в `/opt/kairo-server/server/data/update/` на VPS.
4. Положить туда же `latest.json` по шаблону: `version`, ссылки в `platforms`,
   для десктопа — `signature` из соответствующего `.sig`.
5. Проверить: `curl -s https://kairoupdate.duckdns.org/update/latest.json`.

### Android: чем открывается ссылка на APK

Плагин апдейтера не работает на Android, поэтому там свой путь: клиент сам
читает манифест и отдаёт ссылку на APK системе, а дальше браузер качает
файл и Android предлагает установку.

Отдавать ссылку надо через `@tauri-apps/plugin-opener`, а не через
`shell.open`: последний на Android пытается запустить системный `xdg-open`,
которого там нет, и падает с `Scoped shell IO error: No such file or
directory (os error 2)`. Симптом обманчивый — обновление находится и
предлагается, но кнопка «обновить» не делает ничего.

Плагин требует трёх вещей сразу, иначе не заработает:
`tauri-plugin-opener` в `src-tauri/Cargo.toml`, `.plugin(tauri_plugin_opener::init())`
в `src-tauri/src/lib.rs` и `"opener:default"` в
`src-tauri/capabilities/default.json`.

> Размер сборки. `--apk --debug` без `--target` собирает universal APK под
> четыре ABI с неурезанными отладочными символами Rust — это ~670 МБ на
> скачивание телефону. `--target aarch64` даёт примерно вчетверо меньше и
> ставится на любой современный Android.

> Если перед бэкендом стоит nginx, `/update/` должен проксироваться на
> `127.0.0.1:8787` вместе с остальными маршрутами. Отдельный `location`
> со статикой больше не нужен — но если он остался, он перехватит
> запрос раньше бэкенда, и раздавать будет он.

## Переезд на новый домен (что осталось сделать на сервере)

Клиент уже собирается под `kairoupdate.duckdns.org`. Сертификат выпущен.
Осталось заставить nginx проксировать этот домен на бэкенд.

### Как читать симптом

- **404 от nginx** (в теле ответа видно `nginx/1.18.0 (Ubuntu)`) — запрос
  дошёл до nginx, но попал в server-блок без `proxy_pass`. Проблема в
  `server_name`, бэкенд ни при чём.
- **502 Bad Gateway** — блок правильный, но бэкенд не отвечает:
  `systemctl status kairo-server`.
- **Ошибка TLS / ERR_CONNECTION** — не тот сертификат или домен не резолвится.

### Диагностика

```bash
# какой блок обслуживает домен и куда он проксирует
grep -nE "server_name|listen|proxy_pass|root |location" /etc/nginx/sites-enabled/kairo

# все server_name во всех блоках — ищем, где потерялся kairoupdate
nginx -T 2>/dev/null | grep -n "server_name"

# бэкенд жив? (должно быть {"ok":true})
systemctl status kairo-server --no-pager | head -5
curl -s http://127.0.0.1:8787/health

# проксирует ли старый домен — если да, блок рабочий, дело только в server_name
curl -s -H "Host: kairogoupyrlife.duckdns.org" http://127.0.0.1/health
```

### Применение (всё копируется в терминал целиком)

`/opt/kairo-server` — клон этого репозитория, поэтому конфиг nginx берётся
прямо из него: `server/nginx.example.conf`. Руками редактировать ничего не
нужно.

**Шаг 1. Обновить и пересобрать бэкенд.** Без этого `/update/latest.json`
не заработает даже при правильном nginx — маршрута нет в старом коде.

```bash
cd /opt/kairo-server
git fetch origin
git checkout -B claude/project-audit-2s70zz origin/claude/project-audit-2s70zz
cd /opt/kairo-server/server
sudo -u kairo npm ci --include=dev
sudo -u kairo npm run build
systemctl restart kairo-server
```

Проверка, что новый маршрут поднялся:

```bash
curl -s http://127.0.0.1:8787/health
curl -s http://127.0.0.1:8787/update/latest.json
```

Ожидаем `{"ok":true}` и `{"error":"manifest_not_published",...}`. Вторая
строка — именно то, что нужно: маршрут отвечает, релиз просто ещё не
опубликован. Если вместо неё приходит HTML — бэкенд не пересобрался.

> **Внимание: в боевом клоне бывают локальные правки.** При переключении
> ветки git показал `M server/src/routes/sync.ts` — файл правили прямо на
> сервере, и правка переживает `checkout`. Это значит, что работающий код
> расходится с репозиторием, а `git pull` рано или поздно упрётся в
> конфликт. Перед сборкой всегда проверяй:
>
> ```bash
> cd /opt/kairo-server && git status --short && git diff
> ```
>
> Если правка нужна — перенести её в репозиторий коммитом, а не держать
> только на сервере. Если это мусор — `git checkout -- <файл>`. Молча
> собирать поверх неизвестного диффа нельзя: половина этого документа
> существует ровно потому, что состояние сервера нигде не было записано.

**Шаг 2. Заменить конфиг nginx.**

```bash
cp /etc/nginx/sites-available/kairo /root/kairo-nginx.bak
cp /opt/kairo-server/server/nginx.example.conf /etc/nginx/sites-available/kairo
```

```bash
cat > /etc/nginx/conf.d/websocket-map.conf <<'MAP'
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}
MAP
```

```bash
nginx -t && systemctl reload nginx
```

`reload` выполнится только если `nginx -t` прошёл. Откат, если что-то не так:

```bash
cp /root/kairo-nginx.bak /etc/nginx/sites-available/kairo && nginx -t && systemctl reload nginx
```

**Шаг 3. Проверить снаружи.**

```bash
curl -s  https://kairoupdate.duckdns.org/health
curl -si https://kairoupdate.duckdns.org/update/latest.json | head -1
```

Первое — `{"ok":true}`. Второе — `HTTP/1.1 404` **с JSON-телом**
`manifest_not_published`; это норма. Отличать от `404` со страницей nginx
(HTML) — та означает, что конфиг всё ещё не тот.

Синк по `/health` не проверяется: WebSocket может быть сломан при живом
`/health`. После правки обязательно открой экран SYNC в приложении — он
теперь показывает реальный статус, а не безусловное «облако подключено».

### Порядок вывода старого домена из обращения

1. Починить `kairoupdate` (выше) — все будущие сборки ходят туда.
2. Указать в панели DuckDNS для `kairogoupyrlife` тот же IP `45.151.62.223`
   — тогда уже установленные приложения оживают: и синк, и апдейтер.
3. Опубликовать релиз ≥ 0.4.8 (см. «Обновления приложения»). Устройства
   получают его по старому домену и после установки переезжают на новый.
4. Когда все устройства обновились — убрать блок старого домена из nginx
   и сам домен из DuckDNS.

## Как зайти с НОВОГО устройства

Приватный SSH-ключ есть **только** на исходной Windows-машине
(`%USERPROFILE%\.ssh\id_ed25519`). Пароль по SSH отключён — вход только по ключу.

**Вариант A (рекомендуется) — сгенерировать ещё один ключ:**

1. На новом устройстве: `ssh-keygen -t ed25519 -C "kairo-vps-<имя>"`
2. Показать публичный: Windows `type $env:USERPROFILE\.ssh\id_ed25519.pub`,
   Mac/Linux `cat ~/.ssh/id_ed25519.pub`
3. Дописать эту публичную строку в `/root/.ssh/authorized_keys` на сервере
   (это можно сделать с исходного устройства, где ключ уже работает).

**Вариант B (если пропал доступ ко всем исходным ключам):**

Веб-консоль (VNC) через панель хостера — вход по паролю root. Если пароль тоже
потерян, у хостера кнопка «Сбросить пароль root».

## История

- Изначально начинали ставить как co-host на сервер Observ (`81.90.31.239`) → отказались, взяли отдельный VPS.
- ed25519-ключ на Windows сгенерён один раз, используется для обоих серверов.
- Старый VPS Observ по-прежнему имеет наш ключ в `/root/.ssh/authorized_keys` — если больше не нужен, можно удалить строку с `kairo-vps`.
